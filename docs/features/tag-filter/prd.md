# 태그 필터 PRD

> 요구사항의 상세 동작은 [`spec-fixed.md`](./spec-fixed.md)에 있다.
> 이 문서는 **왜 만드는지**와 **어떤 기술 결정을 했는지**를 다룬다.

## 1. 개요

**문제** — 노트가 쌓일수록 목록을 위에서부터 훑어야만 원하는 주제의 노트를 찾을 수 있다. 선행 태그 기능(`docs/features/tag/`)으로 노트에 태그를 붙일 수 있게 됐지만, 붙인 태그를 노트를 찾는 데 쓸 방법이 아직 없다 — 태그는 각 노트를 열어야만 보이고, 목록 화면 어디에도 노출되지 않는다.

**해결** — 노트 목록 위에 존재하는 모든 태그를 칩으로 나열하는 필터 바를 두고, 칩 하나를 클릭하면 해당 태그가 붙은 노트만 목록에 남긴다. 각 노트 카드에도 태그를 표시해 필터링 없이도 태그 구성을 파악할 수 있게 한다.

**이번 릴리스의 범위** — 단일 태그 선택 필터, 노트 카드 태그 노출. 다중 태그 조합·자동완성·태그별 집계 등은 4장(Out of Scope) 참고.

**성공 기준** — 태그가 붙은 노트가 있는 상태에서, 사용자가 필터 바의 태그 칩 하나를 클릭하면 그 태그가 붙은 노트만 노트 목록에 즉시 남는다. 다시 `[전체]`(또는 선택 중인 칩 재클릭)로 전체 목록으로 복귀할 수 있다.

## 2. 사용자 스토리

### US-1. 태그로 노트 좁혀보기

> 노트가 쌓여가는 사용자로서, 관심 있는 주제의 노트만 골라보고 싶다.
> 노트가 많아질수록 스크롤하며 하나씩 훑는 대신 태그 하나로 바로 좁혀보기 위해서다.

- 노트 목록 위 필터 바에서 원하는 태그 칩을 클릭하면 그 태그가 붙은 노트만 남는다.
- `[전체]` 클릭 또는 선택 중인 칩 재클릭으로 전체 목록으로 돌아온다.
- 상세 동작·유효성 규칙은 `spec-fixed.md` FR-1~FR-3, FR-6 참고.

### US-2. 노트 카드에서 태그 한눈에 보기

> 노트를 훑어보는 사용자로서, 목록 화면에서부터 각 노트에 어떤 태그가 붙어있는지 보고 싶다.
> 노트를 하나씩 열어보지 않고도 필터링 전에 태그 구성을 파악하기 위해서다.

- 각 노트 카드에 그 노트의 태그가 칩으로 표시된다(읽기 전용).
- 상세 동작은 `spec-fixed.md` FR-4 참고.

## 3. 기술 결정 (ADR)

아키텍처 3안(A. 인라인 / B. 유틸 함수 분리 / C. 커스텀 훅 분리) 중 **A. 인라인**을 선택했다. 선행 태그 기능(`docs/features/tag/prd.md` ADR-3, ADR-4)이 같은 갈림길에서 이미 두 번 "유틸/훅 계층 전례 없음"을 이유로 인라인을 택한 방향과 일치한다. 이 선택을 구체화하는 5개의 독립적인 결정을 ADR로 남긴다.

| ADR   | 주제                              | 결정 요약                                                               |
| ----- | --------------------------------- | ----------------------------------------------------------------------- |
| ADR-1 | 필터링·고유 태그 파생 로직의 위치 | `TagFilterBar`/`NoteList` 내부에 인라인 계산. 유틸/훅으로 추출하지 않음 |
| ADR-2 | 필터 상태(`selectedTag`)의 소유자 | `App.tsx`의 로컬 `useState`. `NotesContext` 무변경                      |
| ADR-3 | `TagFilterBar` 컴포넌트 신설 여부 | 신설. `NoteList`에 통합하지 않음                                        |
| ADR-4 | 대상 소멸(FR-6) 처리 방식         | 렌더 시점 파생 가드. `useEffect`로 state를 되돌리지 않음                |
| ADR-5 | 태그 칩 UI 재사용 여부            | 공유 컴포넌트로 추출하지 않음. `NoteItem`/`TagFilterBar`에 각각 작성    |

### ADR-1. 필터링·고유 태그 파생 로직의 위치

**Context**

- 선행 태그 기능은 같은 종류의 갈림길(검증 로직을 유틸로 뺄지)에서 두 번(ADR-3, ADR-4) 모두 "프로젝트에 유틸/훅 계층 전례가 없다"는 이유로 컴포넌트 인라인을 택했다.
- 이번 스펙(`spec-fixed.md`)의 범위는 단일 선택 필터 하나이고, 현재 `db.json`의 노트 수도 4개 수준이라 성능이 축이 되지 않는다.

**Decision**

- 고유 태그 목록은 `TagFilterBar`가 `notes` prop을 받아 매 렌더 `[...new Set(notes.flatMap((n) => n.tags ?? []))].sort((a, b) => a.localeCompare(b))` 형태로 인라인 계산한다.
- 태그로 좁힌 노트 목록은 `NoteList`가 `notes.filter((n) => !activeTag || n.tags?.includes(activeTag))`로 인라인 계산한다.
- 별도 `src/utils/` 파일이나 커스텀 훅을 만들지 않는다.

**Alternatives**

- **B. `src/utils/tags.ts`에 순수 함수로 추출** — RTL 렌더링 없이 vitest로 로직만 독립적으로 단위 테스트할 수 있다는 뚜렷한 장점이 있다. 그러나 이 프로젝트에 `utils`/`lib` 계층 전례가 전혀 없고, 선행 기능 ADR-4가 정확히 같은 이유로 이미 거절한 선택지다. 지금 도입하면 태그 기능 안에서도 "왜 이번만 유틸로 뺐는지" 설명이 필요해진다.
- **C. `useTagFilter(notes)` 커스텀 훅으로 상태+파생값 캡슐화** — 관련 로직이 한 곳에 응집되고 재사용하기 쉽다는 장점이 있다. 그러나 이 프로젝트의 유일한 커스텀 훅은 Context 접근용 `useNotes`뿐이고, `CLAUDE.md`는 UI 로컬 상태를 "각 컴포넌트에 `useState`로 유지"하라고 명시한다 — 새 훅 패턴 도입은 이 원칙과 결이 다르다.

**Consequences**

- (+) 새 파일·새 폴더가 생기지 않는다. 선행 태그 기능과 정확히 같은 스타일이라 리뷰 부담이 없다.
- (−) `TagFilterBar`와 `NoteList` 양쪽에 "고유 태그 추출"과 "태그로 필터링" 로직이 각각 인라인으로 존재해, 같은 종류의 계산이 컴포넌트 경계를 넘어 미묘하게 중복된다(예: 둘 다 `tags ?? []` 방어를 반복).
- (−) notes 배열이 매우 커지면 렌더마다 O(n) 재계산이 반복되지만, 이 프로젝트 규모에서는 문제가 되지 않는다.
- 다시 볼 신호: Out of Scope로 미룬 자동완성·태그별 개수 표시를 실제로 만들 때, 같은 "고유 태그 파생" 로직이 세 번째 지점에서 필요해지는 시점 — 그때는 유틸 추출이 더 이상 과설계가 아니다.

### ADR-2. 필터 상태(`selectedTag`)의 소유자

**Context**

- `App.tsx`는 이미 `selectedNoteId`, `isCreating`을 로컬 `useState`로 들고 props로 내려보낸다. `CLAUDE.md`는 "선택된 노트 id와 UI 전용 상태는 context가 아니라 `App.tsx`의 로컬 상태로 관리"한다고 명시한다.
- `TagFilterBar`(선택)와 `NoteList`(필터링 적용) 두 형제 컴포넌트가 같은 `selectedTag` 값을 공유해야 한다.

**Decision**

- `App.tsx`에 `const [selectedTag, setSelectedTag] = useState<string | null>(null)`를 추가한다. `NotesContext`는 변경하지 않는다.

**Alternatives**

- **`NotesContext`에 필터 상태를 얹기** — 어디서든 `useNotes()`로 접근 가능해진다는 장점이 있다. 그러나 `CLAUDE.md`가 "UI 로컬 상태... context에 넣지 않는다"고 명시적으로 금지하는 패턴이라 논의 대상에서 제외했다.
- **`TagFilterBar`가 자체 상태로 소유** — 새 컴포넌트 하나에 상태가 갇혀 깔끔해 보이지만, `NoteList`도 같은 값을 알아야 필터링할 수 있어 결국 형제 컴포넌트 간 공유를 위해 상위(`App.tsx`)로 끌어올려야 한다(React의 표준적인 "상태 끌어올리기"가 필요한 상황이라 처음부터 상위에 두는 것과 결과가 같다).

**Consequences**

- (+) `selectedNoteId`와 완전히 같은 패턴이라 `App.tsx`를 보는 사람이 바로 이해할 수 있다.
- (−) `App.tsx`의 로컬 상태 개수가 2개에서 3개로 늘어난다.
- 다시 볼 신호: 필터 상태를 `App.tsx` 트리 밖(예: 별도 라우트, URL)에서도 공유해야 하는 요구가 생기는 시점.

### ADR-3. `TagFilterBar` 컴포넌트 신설 여부

**Context**

- 이 프로젝트의 기존 컴포넌트 구조는 책임별로 파일이 분리돼 있다(`Layout`/`NoteList`/`NoteItem`/`NoteEditor`). `NoteList.tsx`는 이미 로딩/에러/빈 상태 3가지 조건부 분기를 갖고 있다.

**Decision**

- `src/components/TagFilterBar.tsx`를 신설한다. `notes: Note[]`, `selectedTag: string | null`, `onSelectTag: (tag: string | null) => void` props를 받아 고유 태그 칩 목록을 렌더링한다. `App.tsx`가 `Layout`의 `sidebar` prop 안에 `<TagFilterBar>`와 `<NoteList>`를 나란히 조립한다.

**Alternatives**

- **`NoteList.tsx` 내부에 필터 바 마크업을 합침** — 새 파일이 늘지 않는다는 장점이 있다. 그러나 `NoteList`가 "목록 렌더링"과 "필터 선택 UI 렌더링"이라는 두 책임을 동시에 갖게 되고, 이미 여러 조건부 분기가 있는 컴포넌트가 더 커진다. FR-1의 "태그가 하나도 없으면 필터 바 자체를 숨김" 조건도 `NoteList`의 기존 loading/error/empty 분기와 뒤섞이게 된다.

**Consequences**

- (+) 각 컴포넌트가 한 가지 일만 한다 — `TagFilterBar`는 태그 선택만, `NoteList`는 목록 렌더링만.
- (+) 기존 컴포넌트 분리 패턴과 일치해 `CLAUDE.md`의 컴포넌트 구현 패턴을 그대로 따른다.
- (−) 새 파일이 1개 늘고, `App.tsx`의 sidebar 조립 마크업이 한 줄 늘어난다.
- 다시 볼 신호: 없음 — 컴포넌트 분리는 나중에 합치기도 쉬운, 되돌리기 쉬운 결정이다.

### ADR-4. 대상 소멸(FR-6) 처리 방식

**Context**

- `spec-fixed.md` FR-6 — 필터링 중인 태그를 가진 노트가 0개가 되면 필터가 자동으로 `[전체]`로 돌아가야 한다.
- 구현 방법은 두 갈래다: (a) `useEffect`로 `selectedTag` state 자체를 실제로 `null`로 되돌리는 것, (b) state는 그대로 두되 렌더링 시점에 "지금 선택된 태그가 현재 고유 태그 목록에 있는지"를 파생시켜 화면에만 반영하는 것.

**Decision**

- (b) 파생 가드를 택한다. `App.tsx`에서 `TagFilterBar`/`NoteList`에 넘기기 직전 `const activeTag = uniqueTags.includes(selectedTag ?? '') ? selectedTag : null`로 계산해 내려준다. 필터 하이라이트와 목록 필터링은 항상 이 `activeTag` 기준으로만 렌더링한다. `selectedTag` state 자체를 되돌리는 effect는 두지 않는다.

**Alternatives**

- **`useEffect(() => { if (selectedTag && !uniqueTags.includes(selectedTag)) setSelectedTag(null) }, [notes])`** — "지금 무엇이 선택되어 있는가"를 `selectedTag` state 하나만 보고 알 수 있다는 장점이 있다. 그러나 파생 가능한 값을 effect로 동기화하는 것은 불필요한 렌더 사이클을 하나 추가하고(렌더 → effect → 재렌더), React가 권장하는 "파생 가능한 값은 effect로 동기화하지 않는다" 원칙에도 어긋난다.

**Consequences**

- (+) effect가 없어 추가 렌더 사이클 없이 항상 최신 `notes` 기준으로 즉시 일관된 화면을 보여준다.
- (+) `App.tsx`에 파생 변수 한 줄만 추가되는 가장 작은 변경이다.
- (−) `selectedTag` state 값과 "화면에 실제로 반영된 필터"가 잠깐 어긋날 수 있다(예: 개발자 도구로 state를 보면 이미 사라진 태그 문자열이 여전히 남아있다) — 디버깅 시 약간 헷갈릴 여지가 있다.
- 다시 볼 신호: `selectedTag` 원본 값을 다른 곳(예: URL 동기화, 로깅)에서도 참조해야 해서 "항상 화면과 일치하는 state"가 필요해지는 시점.

### ADR-5. 태그 칩 UI 재사용 여부

**Context**

- `NoteEditor.tsx:116-129`에 이미 삭제 버튼이 달린 편집 가능한 태그 칩 마크업이 있다(`bg-[#dbe4e7] text-[#586064] rounded-full ... text-sm`).
- 이번 기능은 성격이 다른 칩 2종을 새로 필요로 한다 — `NoteItem`의 읽기 전용 칩(클릭 동작 없음)과 `TagFilterBar`의 클릭 가능한 칩(선택 상태 표시 필요).

**Decision**

- 공유 `TagChip` 컴포넌트로 추출하지 않는다. `NoteItem`과 `TagFilterBar`에 각각 필요한 만큼 JSX를 작성하되, 시각적 일관성을 위해 `NoteEditor`의 기존 칩 클래스를 참고해 맞춘다. 정확한 색상·선택 상태 스타일은 구현 단계에서 `design-system` skill로 확정한다.

**Alternatives**

- **`src/components/TagChip.tsx`로 추출**(`variant: 'editable' | 'readonly' | 'selectable'` 등) — 세 군데(`NoteEditor`·`NoteItem`·`TagFilterBar`)의 스타일이 항상 동기화된다는 장점이 있다. 그러나 이미 병합되어 테스트를 통과한 `NoteEditor.tsx`를 이번 기능 범위에서 굳이 건드리게 되고, 세 변형의 동작 차이(삭제 버튼 유무, 클릭 가능 여부, 선택 상태 표시)가 이미 커서 추출한 컴포넌트가 조건부 분기투성이가 될 가능성이 높다.

**Consequences**

- (+) 이미 병합된 `NoteEditor.tsx`를 건드리지 않아 회귀 위험이 없다.
- (+) 각 칩의 동작이 명확히 분리되어 불필요한 조건부 props가 없다.
- (−) 세 군데의 시각 스타일이 나중에 어긋날 수 있다 — 한 곳만 고치고 나머지를 잊어버리는 사고가 날 여지가 있다.
- 다시 볼 신호: 칩 스타일을 디자인 시스템 차원에서 통일하는 별도 리팩터링 이슈가 생기거나, 칩 변형이 하나 더 늘어나는 시점.

### 4-1. 필터 조건 고도화

| 제외 항목                             | 제외 이유                                                                                                          | 다시 볼 시점                                                         |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| 다중 태그 동시 필터(AND/OR)           | 인터뷰에서 단일 선택으로 확정(`spec-fixed.md` 유효성 규칙). 태그 수가 적은 지금은 조합 필터의 수요가 보이지 않는다 | 노트/태그 수가 늘어 단일 선택으로는 못 좁혀진다는 불편이 확인된 직후 |
| 텍스트 입력으로 태그 검색(칩 클릭 외) | 이번 범위는 "이미 존재하는 태그를 칩으로 고르는" 탐색이다. 텍스트 검색은 오탈자·부분일치 등 별도 설계가 필요하다   | 다중 태그 필터와 함께                                                |
| URL 쿼리 파라미터로 필터 상태 공유    | 인터뷰에서 "유지 안 함(새로고침 시 리셋)"으로 확정. 이 프로젝트엔 라우터가 없다(react-router 미사용)               | 라우팅이 프로젝트에 도입되는 시점                                    |

### 4-2. 태그 탐색 보조 기능

| 제외 항목                         | 제외 이유                                                                                                                                                                     | 다시 볼 시점                       |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 태그 자동완성(입력 중 제안)       | 선행 태그 기능 PRD가 이미 "필터링 기능과 함께"로 미뤄뒀다. 전체 태그 목록을 조회하는 경로 자체는 이번 기능(ADR-1)이 만들지만, 입력창 제안 UI·매칭 로직은 별도 설계가 필요하다 | 자동완성 요구가 실제로 나오는 시점 |
| 태그별 노트 개수 표시(칩 옆 배지) | 집계 로직과 칩 마크업 변경이 추가로 필요하다. 이번 범위인 "필터링 가능하게 만드는" 단계를 넘어선다                                                                            | 태그 자동완성과 함께               |
| 태그 기준 정렬/그룹핑             | 정렬 기준(`createdAt`/`updatedAt`)에 태그를 추가하려면 `NoteList` 목록 UI 자체의 변경이 필요하다                                                                              | 태그 자동완성과 함께               |

### 4-3. 태그 관리 기능

| 제외 항목                           | 제외 이유                                                                                                                              | 다시 볼 시점                                     |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 태그 이름 일괄 변경/병합/삭제(전역) | 선행 태그 기능 ADR-1이 태그를 노트 문서에 내장하기로 해, 일괄 변경은 노트 전체 순회가 필요하다. 이번 필터 기능도 그 구조를 그대로 쓴다 | 태그 수가 늘어 오타·중복 정리 수요가 생기는 시점 |
| 태그별 색상 지정                    | 선행 태그 기능 PRD가 이미 미뤄둔 항목이며, 이번 필터 기능과도 직접 관련이 없다                                                         | 태그 관리 화면과 함께                            |

> 이번 구조(ADR-1~5)가 위 기능들을 막지는 않는다. 고유 태그 파생 로직을 유틸로 옮기고 나면 자동완성·개수 표시 모두 그 위에 얹을 수 있다.

## 5. 용어 정의

`spec-fixed.md`의 정의를 그대로 따른다.

| 용어      | 정의                                                                                                          |
| --------- | ------------------------------------------------------------------------------------------------------------- |
| 선택      | 필터 바에서 태그 칩을 클릭해 그 태그를 필터 조건으로 삼는 것. 서버에 아무것도 기록하지 않는 순수 UI 상태 변경 |
| `[전체]`  | 필터가 해제된 기본 상태를 나타내는 특수 칩 — 모든 노트를 보여준다                                             |
| 대상 소멸 | 필터링 중인 태그를 가진 노트가 0개가 되어 필터를 유지할 근거가 사라지는 것                                    |
