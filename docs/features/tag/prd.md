# 태그 기능 PRD

> 요구사항의 상세 동작은 [`spec-fixed.md`](./spec-fixed.md)에 있다.
> 이 문서는 **왜 만드는지**와 **어떤 기술 결정을 했는지**를 다룬다.

## 1. 개요

**문제**
노트가 쌓일수록 제목만으로 원하는 노트를 다시 찾기 어렵다. `content` 검색이나 태그 같은 분류 축이 없어서, 비슷한 주제의 노트를 묶거나 구분할 방법이 제목을 기억하는 것뿐이다.

**해결**
노트에 자유 텍스트 태그를 붙여 주제/카테고리를 표시할 수 있게 한다. 이번 릴리스는 태그를 **붙이고 확인할 수 있게 만드는 단계**에 집중한다 — 태그를 활용해 검색·필터링하는 기능은 이번 범위가 아니다 (4장 참고).

**이번 릴리스의 범위**

- `NoteEditor`에서 태그 추가/삭제 UI 제공
- 태그 입력 시 trim + 대소문자 무시 중복 검사
- [저장] 버튼을 눌렀을 때만 `tags`가 서버에 반영 (title/content와 동일한 반영 시점)

**성공 기준**

- 노트에 태그를 추가하고 저장한 뒤 다시 그 노트를 열었을 때 태그가 그대로 남아 있다.
- 같은 태그(대소문자만 다른 경우 포함)를 두 번 추가해도 하나만 남는다.
- 태그를 삭제하고 저장하면 서버에서도 제거된다.

## 2. 사용자 스토리

### US-1. 노트에 태그 붙이기

> 노트를 정리하려는 사용자로서, 노트에 태그를 붙이고 싶다.
> 나중에 비슷한 주제의 노트를 같은 이름으로 묶어두기 위해서다.

- `NoteEditor`의 태그 입력창에 텍스트를 입력해 추가한다.
- 유효성 검사(빈 문자열, 중복)는 `spec-fixed.md`를 정본으로 한다.

### US-2. 노트에서 태그 삭제하기

> 노트를 정리하려는 사용자로서, 잘못 붙였거나 더 이상 유효하지 않은 태그를 지우고 싶다.
> 태그 목록이 노트의 실제 주제를 정확히 반영하도록 유지하기 위해서다.

- 각 태그 칩의 삭제(X) 버튼으로 제거한다.
- [저장]을 누르기 전까지는 로컬 상태에서만 제거된다.

### US-3. 노트에 붙은 태그 확인하기

> 노트를 다시 열어보는 사용자로서, 이 노트에 어떤 태그가 붙어 있는지 한눈에 보고 싶다.
> 제목·내용을 다시 읽지 않고도 노트의 주제를 파악하기 위해서다.

- `NoteEditor`에서 노트를 선택하면 저장된 태그가 칩 형태로 표시된다.

## 3. 기술 결정 (ADR)

3안 비교(데이터 구조 / API 레이어 / 상태관리 / 태그 즉시 저장 동작 / 컴포넌트 구조 / 기존 패턴 일관성 / 테스트 용이성) 결과 **A안(컴포넌트 인라인 — 기준선)** 을 선택했다. `title`/`content`와 동일한 패턴(로컬 `useState`, 저장 버튼 클릭 시 일괄 반영, 인라인 유효성 검사)을 그대로 따르고, 새 폴더(`hooks/`, `utils/`)나 새 API 함수를 도입하지 않는다.

| ADR   | 주제                                | 결정 요약                                                                                    |
| ----- | ----------------------------------- | -------------------------------------------------------------------------------------------- |
| ADR-1 | 태그 데이터 저장 형태               | `Note.tags: string[]` 노트 문서에 내장. 별도 컬렉션 없음                                     |
| ADR-2 | 태그 전용 API 함수 도입 여부        | 신설하지 않음. 기존 `updateNote`(PATCH)로 title/content와 함께 일괄 전송                     |
| ADR-3 | 태그 상태의 소유자와 서버 반영 시점 | `NoteEditor`의 로컬 `useState<string[]>`. `NotesContext` 무변경, [저장] 클릭 시 한 번에 반영 |
| ADR-4 | 중복/유효성 검사 로직의 위치        | `NoteEditor` 내부 `handleAddTag`에 인라인. 별도 유틸/훅으로 추출하지 않음                    |

### ADR-1. 태그 데이터 저장 형태

**Context**

- json-server 백엔드는 조인을 지원하지 않는다. 노트마다 태그를 보여줘야 하는데, 이번 릴리스는 태그 활용(필터/검색, Out of Scope 4-1)이 범위 밖이라 전역 태그 조회 경로 자체가 필요 없다.
- `Note` 타입은 현재 `id/title/content/createdAt/updatedAt`만 갖고 있고, `tags` 필드는 "강의에서 추가할 것"이라는 주석과 함께 의도적으로 비어 있다(`src/types/note.ts:7`).

**Decision**

- `Note` 타입에 `tags: string[]` 필드를 추가한다. 별도 `tags` 컬렉션/엔드포인트 없이 노트 문서 내부 배열로만 저장한다.

**Alternatives**

- **별도 `tags` 컬렉션으로 정규화**(예: `/tags` 리소스, 노트는 `tagIds: string[]`로 참조) — 태그 이름 변경/병합 시 한 곳만 고치면 되고 전역 태그 집계가 쉽다는 장점이 있다. 그러나 json-server는 조인이 없어 노트에 태그를 표시하려면 매번 `/tags`를 추가 조회해 클라이언트에서 합쳐야 하고, 이번 범위엔 전역 태그 조회 기능 자체가 없어(Out of Scope 4-1) 이 이점을 쓸 곳이 없다.
- **노트에 `tagIds: string[]`만 두고 태그 메타는 별도 관리** — 위와 같은 조인 문제를 그대로 안으면서, 정규화의 이점(이름 일괄 변경)도 이번 범위(Out of Scope 4-2)에서는 쓰지 않는다.

**Consequences**

- (+) `updateNote` PATCH 한 번으로 `tags`까지 함께 저장/조회된다 — 추가 요청이나 클라이언트 조인 로직이 없다.
- (−) 태그 이름 일괄 변경/병합(Out of Scope 4-2)을 나중에 만들면 노트 전체를 순회해야 한다. 지금은 범위 밖이라 문제되지 않는다.
- (−) 노트가 매우 많아지고 전역 태그 집계(자동완성, 필터)가 필요해지면 클라이언트가 노트 전체를 스캔해야 해 비효율적이다.
- 다시 볼 신호: 태그 자동완성/필터링(Out of Scope 4-1)을 실제로 만들 때 노트 전체 스캔 비용이 문제되면 재검토한다.

### ADR-2. 태그 전용 API 함수 도입 여부

**Context**

- `src/api/notes.ts`의 `updateNote(id, updates: Partial<Note>)`는 이미 임의의 `Note` 필드 부분 갱신을 지원한다. `Note.tags`가 추가되면 코드 변경 없이 `updates`에 `tags`를 포함해 호출할 수 있다.
- `CLAUDE.md`의 API 호출 패턴은 새 API 함수를 추가할 때 `API_URL` 하드코딩, `res.ok` 체크, 한국어 `Error` throw를 반복하라고 명시한다 — 함수를 늘릴수록 보일러플레이트가 늘어난다.

**Decision**

- 태그 전용 API 함수를 만들지 않는다. `NoteEditor`의 `handleSave`에서 `updateNote(id, { title, content, tags })`로 title/content와 함께 한 번에 PATCH한다.

**Alternatives**

- **`updateNoteTags(id, tags: string[])` 같은 전용 함수 신설** — 호출부에서 의도가 더 명확해지고(태그만 바꾼다는 게 함수명으로 드러남), 태그만 바꾸는 다른 흐름(예: 목록 화면 인라인 태그 편집)이 생기면 재사용할 수 있다는 장점이 있다. 그러나 A안은 [저장] 버튼 한 번에 모든 필드를 일괄 반영하기로 했으므로(ADR-3) 태그만 따로 PATCH할 시점이 없다 — 지금 만들면 쓰이지 않는 함수가 된다.

**Consequences**

- (+) `api/notes.ts`에 코드가 추가되지 않는다. 새 함수의 네이밍·에러 메시지를 새로 고민할 필요가 없다.
- (−) 태그만 부분 저장하고 싶은 미래 요구(예: 노트 목록에서 태그만 빠르게 편집)가 생기면 그때 `updateNote` 재사용 여부를 다시 판단해야 한다.
- 다시 볼 신호: `NoteEditor` 밖(`NoteList`/`NoteItem` 등)에서 태그만 단독으로 저장하는 흐름이 생기는 시점.

### ADR-3. 태그 상태의 소유자와 서버 반영 시점

**Context**

- `NoteEditor.tsx`는 `title`, `content`를 각각 `useState`로 들고, `selectedNoteId`/`isCreating`이 바뀔 때 `useEffect`로 동기화한다(`NoteEditor.tsx:12-27`). 서버 반영은 `handleSave` 실행 시에만 일어난다(낙관적 업데이트 없음 — `CLAUDE.md` State Management 절).
- `CLAUDE.md`는 UI 로컬 상태(선택된 id, 편집 중인 폼 값 등)를 컴포넌트에 `useState`로 유지하고 context에 넣지 말라고 명시한다.

**Decision**

- `tags`도 `title`/`content`와 동일하게 `NoteEditor`의 로컬 `useState<string[]>`로 관리한다. 태그 추가/삭제는 이 로컬 배열만 즉시 바꾸고, 서버 반영은 `handleSave`에서 `updateNote(id, { title, content, tags })` 한 번으로 처리한다. `NotesContext`는 변경하지 않는다.

**Alternatives**

- **커스텀 훅(`useTags`)으로 상태 분리** — 태그 로직(추가/삭제/중복검사)이 컴포넌트 밖으로 빠져 `NoteEditor`가 얇아지고, 훅 단위로 테스트할 수 있다는 장점이 있다. 그러나 프로젝트에 폼 상태용 커스텀 훅 전례가 없고(현재 훅은 context용 `useNotes` 하나뿐), `src/hooks/` 폴더를 새로 만들면 `CLAUDE.md`의 폴더 구조 절도 함께 갱신해야 한다. 태그 하나 때문에 새 계층을 들이는 건 이번 범위에 비해 과하다고 판단했다.
- **`NotesContext`에 태그 상태를 얹기** — `CLAUDE.md`가 "UI 로컬 상태... context에 넣지 않는다"고 명시적으로 금지하는 패턴이라 논의 대상에서 제외했다.

**Consequences**

- (+) `title`/`content`와 완전히 같은 패턴이라 `NoteEditor`를 처음 보는 사람도 바로 이해할 수 있다. `useEffect` 동기화에 `setTags(selectedNote.tags ?? [])` 한 줄만 추가하면 된다.
- (−) `NoteEditor.tsx`의 책임(제목/내용/태그 상태 + 저장 + 유효성 검사)이 한 파일에 계속 쌓인다. 태그 로직이 커지면(예: 색상/설명 속성 추가) 파일을 분리해야 하는 시점이 온다.
- (−) 태그 add/remove/중복검사를 다른 화면에서도 써야 하면 로직을 복붙하거나 그때 훅으로 추출해야 한다.
- 다시 볼 신호: `NoteEditor.tsx`가 크게 비대해지거나, 태그 편집 UI가 `NoteEditor` 밖(목록, 별도 모달 등)에도 필요해지는 시점.

### ADR-4. 중복/유효성 검사 로직의 위치

**Context**

- `spec-fixed.md`는 trim 후 빈 문자열 거부, 대소문자 무시 중복 판단, 원문 그대로 저장을 요구한다.
- `NoteEditor`는 이미 저장 시점에 `if (!title.trim()) { console.error(...); return; }` 형태의 인라인 유효성 검사를 쓴다(`NoteEditor.tsx:30-33`) — 별도 검증 함수나 유틸 없이 컴포넌트 안에서 바로 처리하는 게 기존 패턴이다.

**Decision**

- 태그 추가 시 유효성 검사(trim, 빈 문자열 거부, 대소문자 무시 중복판단)를 별도 함수/파일로 추출하지 않고, `NoteEditor` 내부의 신규 `handleAddTag` 함수 안에 인라인으로 작성한다. 실패 시 `title` 검증과 동일하게 `console.error`로만 로깅한다(`alert` 미사용).

**Alternatives**

- **`src/utils/tags.ts`에 순수 함수(`normalizeTag`, `isDuplicateTag` 등)로 추출** — 컴포넌트 렌더링 없이 vitest로 로직만 직접 단위 테스트할 수 있다는 뚜렷한 장점이 있다. 그러나 프로젝트에 이런 순수 로직 계층(`utils`/`lib`) 전례가 전혀 없고, `title` 검증도 지금 인라인으로 처리되는 상태라 태그만 다른 계층으로 빼면 같은 컴포넌트 안에서 검증 방식이 두 갈래로 나뉜다.

**Consequences**

- (+) `title` 검증과 위치·스타일이 동일해, 코드 리뷰에서 "왜 태그만 다르게 처리했는지" 설명할 필요가 없다.
- (−) 이 로직은 `NoteEditor`를 RTL로 렌더링해야만 테스트할 수 있다. 현재 프로젝트에 테스트 파일이 하나도 없다는 점(`CLAUDE.md` "발견된 불일치")과 맞물려, 나중에 테스트를 추가할 때 진입장벽이 된다.
- (−) 같은 중복판단 로직이 필요한 곳이 늘어나면(예: Out of Scope 4-2의 태그 관리 기능) 그때 컴포넌트에서 로직을 뜯어내는 리팩터링이 선행돼야 한다.
- 다시 볼 신호: 이 검증 로직을 `NoteEditor` 밖에서도 재사용해야 하는 요구가 생기는 시점(태그 관리 화면, 자동완성 검증 등).

## 4. Out of Scope

### 4-1. 태그 활용 기능

| 제외 항목                         | 제외 이유                                                                                                   | 다시 볼 시점                           |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 태그로 노트 필터링/검색           | 이번 릴리스는 태그가 **쌓이게 만드는** 단계. 실제 데이터 없이 필터 UI를 만들 근거가 없다                    | 실제 노트에 태그가 어느 정도 쌓인 직후 |
| 기존 태그 자동완성 (입력 중 제안) | 전체 태그 목록을 조회하는 경로가 필요하다. 현재 구조는 노트별 `tags` 배열만 있고 전역 태그 집계 경로가 없다 | 필터링 기능과 함께                     |
| 태그 기준 정렬/그룹핑             | 정렬 기준(`createdAt`/`updatedAt`)에 태그를 추가하려면 목록 UI 자체의 변경이 필요하다                       | 필터링 기능과 함께                     |
| 태그별 노트 개수 표시             | 집계 로직이 필요하고, 이번 범위인 "붙이고 확인" 단계를 넘어선다                                             | 필터링/자동완성과 함께                 |

> 이번 구조(노트 문서에 `tags: string[]` 내장)가 위 기능들을 원천적으로 막지는 않는다. 노트 전체를 순회해서 얹을 수 있다.

### 4-2. 태그 관리 기능

| 제외 항목                                       | 제외 이유                                                                                                | 다시 볼 시점                                     |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 태그 이름 일괄 변경(rename)                     | 모든 노트를 순회하며 같은 이름의 태그를 찾아 바꿔야 하는 다중 노트 작업 — 이번 범위는 노트 1개 단위 편집 | 태그 사용량이 늘어 오타/명칭 정리 수요가 생길 때 |
| 태그 병합(merge)                                | rename과 동일하게 다중 노트 영향 범위를 가진다                                                           | rename과 함께                                    |
| 전역 태그 목록 관리 화면(태그만 따로 보기/삭제) | 별도 뷰·라우팅이 필요하고, 지금은 `NoteEditor` 하나로 UI를 한정하기로 했다                               | 태그 활용 기능 착수 시점                         |
| 태그 개수 제한(노트당 최대 N개)                 | `spec-fixed.md`에 명시된 제약이 아니며, 필요성이 검증되지 않았다                                         | 실사용 중 UX 문제가 보고될 때                    |

### 4-3. 표현/UI

| 제외 항목                                  | 제외 이유                                                                                           | 다시 볼 시점              |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------- | ------------------------- |
| 태그 색상/카테고리 지정                    | 태그가 이름 이상의 속성(색·설명)을 갖는 것은 데이터 구조 자체를 바꾼다                              | 태그 활용도가 검증된 이후 |
| 태그 클릭 시 필터 진입                     | 필터링 기능(4-1)에 종속된다                                                                         | 필터링 기능과 함께        |
| 태그 목록 화면(노트 목록에서 태그 칩 노출) | `spec-fixed.md`는 태그 UI 위치를 `NoteEditor`로 한정한다. `NoteList`/`NoteItem` 변경은 이번 범위 밖 | 필터링 기능과 함께        |

### 4-4. 데이터/인프라

| 제외 항목                                              | 제외 이유                                                                                                           | 다시 볼 시점                                                                   |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 별도 태그 테이블/컬렉션로 정규화                       | `spec-fixed.md`에서 노트 객체 내장 배열로 명시적으로 확정됨 (json-server 기반)                                      | 태그가 이름 이상의 속성을 가질 때                                              |

## 5. 용어 정의

| 용어            | 정의                                                                                                                   |
| --------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 태그(Tag)       | 노트에 붙이는 자유 텍스트 라벨. `Note.tags: string[]`로 저장되며, 값 자체는 원문 그대로 유지된다                       |
| 칩(Chip)        | 태그 하나를 화면에 표시하는 UI 단위. 삭제(X) 버튼을 포함한다                                                           |
| 확정(중복 판단) | 태그 추가 시 기존 태그와 대소문자 무시 비교로 동일 여부를 판단하는 것. `"React"`와 `"react"`는 같은 태그로 취급        |
| 반영(저장 시점) | 로컬 상태(`useState<string[]>`)의 태그 변경 사항을 [저장] 버튼 클릭 시 `updateNote` 호출로 서버에 실제로 전송하는 시점 |
