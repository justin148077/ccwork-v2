# security-review

리팩터링이 끝나고 커밋하기 직전에 돌리는 점검 스킬이다. `npx tsc --noEmit`, `npm audit`, `.env` 노출 여부를 스캔해 발견 사항을 세 등급으로 분류하고, 그중 "즉시 수정 필요"만 개발자 승인 후 처리한다. 이 스킬은 새 코드를 짜지 않는다 — 기존 코드/의존성의 문제를 찾아 분류하고, 승인된 것만 최소한으로 고친다.

입력: 이슈 번호 (`$ARGUMENTS`, 예: `/security-review 1`)

## 왜 스캔과 수정을 분리하는가

`npm audit`이나 타입 에러 목록에는 실제로 위험한 것도 있지만, 이미 알려져 있고 이번 작업과 무관한 것(예: 개발 의존성의 낮은 심각도 취약점으로 이 프로젝트에선 영향이 없는 것)도 섞여 있다. 발견하자마자 바로 고치면 "즉시 수정 필요"와 "무시해도 되는 것"을 구분하는 판단을 사람이 검토할 기회 없이 건너뛰게 된다. 그래서 `tdd-refactor`와 같은 원칙 — 먼저 분류해서 보여주고, 승인받은 것만 고친다.

## 실행 순서

### 1. 타입 오류 수집

```bash
npx tsc --noEmit
```

출력 전체(에러 목록)를 수집한다. 출력이 없으면 타입 오류 없음.

### 2. 의존성 취약점 수집

```bash
npm audit
```

심각도(critical/high/moderate/low)별로 몇 건인지, 어떤 패키지인지 수집한다. `package-lock.json`이 없으면 이 단계는 건너뛰고 그 사실을 보고에 남긴다.

### 3. `.env` 노출 위험 확인

이 프로젝트는 Vite 기반이다 — Vite는 `.env`의 변수 중 `VITE_` 접두사가 붙은 것만 `import.meta.env`를 통해 클라이언트 번들에 포함시킨다. 즉 위험은 두 방향이다: **커밋되면 안 되는 `.env` 자체가 커밋된 경우**, 그리고 **`VITE_` 접두사 때문에 원래 비밀이어야 할 값이 클라이언트에 그대로 노출되는 경우**.

```bash
# .env가 실수로 git에 추적되고 있는지 (gitignore돼 있어도 -f로 강제 추가됐을 수 있음)
git ls-files | grep -E '^\.env'

# src/ 코드가 import.meta.env 또는 process.env를 직접 참조하는 곳이 있는지
grep -rn "import\.meta\.env\|process\.env" src/
```

- `git ls-files` 결과가 있으면 그 자체로 "즉시 수정 필요"(비밀 값이 저장소 히스토리에 들어갔을 가능성).
- `src/`에서 `import.meta.env.VITE_*` 참조를 찾았으면, 그 변수 이름에 `SECRET`/`KEY`/`TOKEN`/`PASSWORD` 같은 비밀스러운 이름이 들어 있는지 확인한다 — `VITE_` 접두사가 붙은 값은 설계상 클라이언트에 그대로 노출되므로, 이런 이름이 있으면 "즉시 수정 필요"로 분류한다.
- 이 프로젝트는 현재 `.env` 파일 자체가 없고 `src/`에 `import.meta.env`/`process.env` 참조도 없다(`CLAUDE.md`의 "API 호출 패턴" — `API_URL`은 환경변수 없이 하드코딩) — 이 경우 3번은 "해당 없음"으로 짧게 보고하고 넘어간다. 없는 것을 억지로 문제 삼지 않는다.

### 4. 세 등급으로 분류해 보고

1~3에서 모은 항목을 아래 기준으로 나눠 목록으로 제시한다. 판단 근거를 항목마다 한 줄씩 붙인다.

- **즉시 수정 필요** — 보안 위험(비밀 노출, `.env` 커밋, critical/high 취약점) 또는 빌드 실패 수준(타입 오류로 `npm run build`가 깨지는 경우)
- **권장 수정** — 코드 품질 저하이지만 당장 위험하거나 빌드를 막지는 않는 것(예: moderate/low 취약점 중 실제 공격 경로가 이 프로젝트에 없는 것, 타입 오류는 아니지만 `any` 남용 등 — 단, 이 단계는 1~3에서 수집한 것 범위 안에서만 판단하고 새로 코드를 뒤져 품질 이슈를 찾으러 다니지 않는다)
- **무시 가능** — false positive이거나 이 프로젝트에 의도적으로 존재하는 패턴(예: `devDependencies`에만 있는 취약점, 실제로 실행되지 않는 빌드 도구 체인의 낮은 심각도 이슈)

각 항목에 근거를 적을 때 "왜 이 등급인지"를 분명히 한다 — 특히 "무시 가능"으로 내리는 항목은 무시해도 되는 이유(영향 범위, 실행 경로 없음 등)를 반드시 설명한다. 근거 없이 등급만 매기지 않는다.

### 5. 승인 대기 — 하드 게이트

분류 결과를 제시하고 멈춘다. **판단이 필요한 항목(즉시 수정 필요, 권장 수정 모두)은 개발자의 명시적 승인 없이 고치지 않는다.** "즉시 수정 필요 항목 진행해줘", "1번만 고쳐줘"처럼 승인이 와야 6번으로 넘어간다. "권장 수정" 항목은 이 스킬의 처리 대상이 아니다 — 개발자가 원하면 별도로 `tdd-refactor`를 통해 다루도록 안내한다(코드 구조를 바꾸는 성격이면), 새 코드가 필요하면 그건 이 스킬의 범위 밖임을 알린다.

### 6. 승인된 "즉시 수정 필요" 항목 처리

승인된 항목만 하나씩 고친다.

- 타입 오류: 최소한의 수정으로 타입을 맞춘다 — 오류를 없애려고 `any`나 `@ts-ignore`로 덮지 않는다.
- 의존성 취약점: `npm audit fix`(force 아닌 일반 버전)로 해결 가능하면 그것부터 시도한다. **`npm audit fix --force`는 쓰지 않는다** — 메이저 버전을 강제로 올려 호환성을 깨뜨릴 수 있다. 일반 `fix`로 해결이 안 되는 취약점은 직접 고치지 말고 개발자에게 상황(어떤 메이저 업그레이드가 필요한지)을 보고한다.
- `.env` 노출: 실제 비밀 값 자체를 다루는 조치(키 교체 등)는 이 스킬의 권한 밖이다 — 코드에서 노출 경로를 없애는 것(예: 잘못 참조된 코드 제거)까지만 하고, 이미 노출된 값의 무효화/교체는 개발자에게 별도로 안내한다.
- 매 항목 수정 후:
  ```bash
  npm test
  ```
  로 회귀가 없는지 확인한다.

### 7. 재스캔으로 클린 상태 확인

1~3을 다시 실행해 "즉시 수정 필요" 항목이 더 이상 없는지 확인한다. 여기서 "클린"은 즉시 수정 필요 항목이 없다는 뜻이지, 권장 수정/무시 가능 항목까지 0건이라는 뜻이 아니다 — 그 두 등급은 이 스킬의 처리 대상이 아니므로 남아 있는 게 정상이다.

### 8. 결과 요약

무엇을 몇 건씩 발견했는지(등급별), 그중 무엇을 고쳤는지, 재스캔 결과, 그리고 "권장 수정"으로 남은 항목이 있다면 다음에 어떻게 다룰지(예: 다음 `tdd-refactor` 실행 시 함께 검토) 안내한다. 커밋은 하지 않는다 — 개발자가 최종적으로 diff를 보고 커밋 여부를 결정한다.

## 제약 — 반드시 지킬 것

- **판단이 필요한 항목은 반드시 개발자 승인 후에만 수정한다.** 심각도가 명백해 보여도 임의로 먼저 고치지 않는다.
- **테스트 파일(`*.test.ts` / `*.test.tsx`)을 수정하지 않는다.**
- **`npm audit fix --force`를 쓰지 않는다.**

## 하지 않을 것

- 스캔 결과를 분류만 하지 않고 곧바로 고치지 않는다 — 5번 승인 게이트를 항상 거친다.
- "권장 수정"이나 "무시 가능" 항목을 이 스킬 실행 중에 함께 고치지 않는다 — 승인된 "즉시 수정 필요" 항목만 처리한다.
- 등급을 매길 때 근거 없이 "무시 가능"으로 넘기지 않는다 — 왜 무시해도 되는지 설명한다.
- 타입 오류를 `any`/`@ts-ignore`로 가려서 통과시키지 않는다.
- 커밋하거나 푸시하지 않는다.
