# tdd-refactor

TDD의 Refactor 단계만 담당하는 스킬이다. `tdd-green`이 만들어 둔 "테스트 전부 통과" 상태를 입력으로 받아, **동작은 그대로 두고 구조만 개선**한다. 리팩터링 대상을 발견해도 곧바로 고치지 않고 먼저 목록으로 제시해 승인받으며, 승인된 항목을 하나씩 고칠 때마다 즉시 테스트를 돌려 무회귀를 확인한다.

입력: 이슈 번호 (`$ARGUMENTS`, 예: `/tdd-refactor 1`)

## 왜 "목록 제시 → 승인 → 하나씩"인가

리팩터링은 정답이 하나가 아니다 — 같은 중복을 봐도 사람마다 추출 방식이 다르고, 어떤 팀은 헬퍼 함수를, 어떤 팀은 인라인 유지를 선호한다. 개발자 승인 없이 바로 고치면 이 프로젝트의 암묵적 선호(예: `docs/features/tag/prd.md`의 ADR-4처럼 "별도 유틸로 추출하지 않는다"는 의도적 결정)와 충돌할 수 있다. 그래서 `test-scenarios`가 시그니처를, 이 스킬이 리팩터링 대상을 먼저 사람에게 확인받는 것은 같은 원칙이다. 그리고 하나씩 고치고 바로 테스트를 돌리는 것은 `tdd-red`/`tdd-green`과 동일한 이유다 — 여러 개를 한꺼번에 고치면 어떤 변경이 회귀를 일으켰는지 구분하기 어렵다.

## 실행 순서

### 1. 프로젝트 컨벤션 파악

루트 `CLAUDE.md`를 읽어 네이밍 패턴, 컴포넌트/API 구현 패턴, 상태 관리 원칙 등 이 프로젝트의 컨벤션을 파악한다. 5단계의 "컨벤션 불일치" 판단 기준이 된다.

### 2. 시작 전 전체 테스트 통과 확인

```bash
npm test
```

전체가 통과하는 상태에서만 리팩터링을 시작한다. **하나라도 실패 중이면 중단**하고, 아직 Green 단계가 끝나지 않은 것이니 `tdd-green`을 먼저 실행하라고 안내한다 — 실패하는 테스트가 있는 상태에서 구조를 바꾸면 "리팩터링이 회귀를 일으켰는지" "원래부터 실패였는지" 구분할 수 없다.

### 3. 리팩터링 대상 파일 식별

대상 파일 목록은 **커밋된 변경과 미커밋 변경을 합쳐서** 구한다:

```bash
git diff main...HEAD --name-only -- src/
git status --porcelain -- src/
```

이 프로젝트를 포함해 많은 작업이 커밋 전 상태로 진행되므로(예: `tdd-green`이 방금 만든 구현이 아직 커밋되지 않은 경우), `git diff main...HEAD`만 보면 커밋되지 않은 파일이 통째로 빠진다. 두 명령 결과의 파일 경로를 합집합으로 모으고, 다음을 제외한다:

- 테스트 파일(`*.test.ts` / `*.test.tsx`)
- `src/` 밖의 파일 (문서, 설정 등)

이슈 문서 `docs/features/*/issue-{번호}.md`가 있으면 이번 작업의 배경(어떤 AC/시나리오를 위한 코드인지)을 파악하는 데 참고한다 — 단, 대상 파일 목록 자체는 git 결과가 기준이고 이슈 문서로 범위를 넓히거나 좁히지 않는다.

남은 파일마다 아래 5가지 범용 점검 기준으로 검토하고, 무엇을 발견했는지만 기록한다(**아직 고치지 않는다**):

- **중복 제거** — 같은 로직이 반복되는가
- **네이밍 명확성** — 의도를 드러내는 이름인가
- **단일 책임** — 하나의 함수/컴포넌트가 너무 많은 일을 하는가
- **불필요한 복잡도** — 매직 넘버, 과도한 중첩, 불필요한 추상화
- **`CLAUDE.md` 컨벤션 불일치** — 1단계에서 파악한 프로젝트 패턴과 어긋나는 코드

### 4. 목록 제시 및 승인 대기 — 하드 게이트

발견한 항목을 파일별로 정리해 채팅에 제시한다. 각 항목에 파일 경로, 무엇을, 왜(위 5가지 기준 중 어디 해당하는지), 어떻게 고칠지 한 줄 제안을 붙인다. 발견한 게 없으면 "리팩터링할 게 없습니다"로 여기서 끝낸다.

**여기서 멈춘다.** 목록을 제시한 같은 응답 안에서 바로 수정에 들어가지 않는다. 개발자가 "전부 진행", "1번만", "이건 빼고 진행" 등으로 명시적으로 범위를 확정해야 5번으로 넘어간다. 개발자가 특정 항목에 다른 접근을 요구하면 그 항목만 다시 제안하고 승인을 기다린다.

### 5. 승인된 항목을 하나씩 적용

승인된 항목 하나를 고치고 즉시:

```bash
npm test
```

**통과하면**: 다음 항목으로 넘어간다.

**실패하면**: 즉시 롤백한다 — 방금 만든 편집만 되돌린다(`git checkout`/`git reset` 같은 파일 단위 되돌리기는 쓰지 않는다. 리팩터링 시작 전부터 있던 다른 미커밋 변경까지 함께 날아갈 수 있어서다). 되돌린 뒤 같은 항목에 다른 접근으로 한 번 더 시도한다. 그래도 테스트가 깨지면 그 항목은 건너뛰고("스킵 — 이유: ...") 다음 항목으로 넘어간다 — 리팩터링 하나 때문에 전체 진행을 막지 않는다.

### 6. 전체 마무리

승인된 항목을 모두 처리했으면 전체 테스트를 한 번 더 돌려 최종 통과를 확인한다:

```bash
npm test
```

### 7. 결과 요약

리팩터링 전후 변경을 요약한다 — 어떤 파일에서 무엇을 어떻게 고쳤는지(적용된 항목), 무엇을 스킵했는지(이유 포함), 최종 테스트 결과. 커밋은 하지 않는다 — 개발자가 diff를 검토한 뒤 직접 커밋 여부를 결정한다.

## 제약 — 반드시 지킬 것

- **새 기능을 추가하지 않는다.** 동작(테스트가 검증하는 범위)은 리팩터링 전후로 완전히 동일해야 한다.
- **테스트 파일(`*.test.ts` / `*.test.tsx`)을 수정하지 않는다.** 테스트가 리팩터링 후 코드와 안 맞아 보여도, 그건 프로덕션 코드 쪽 문제이지 테스트를 고칠 이유가 아니다.
- **`src/` 디렉토리 밖을 수정하지 않는다.**
- **3번에서 식별한 대상 파일 범위 밖을 수정하지 않는다.** 리팩터링하다 보면 옆 파일도 손대고 싶은 유혹이 들어도, 이번 작업이 건드리지 않은 파일은 범위 밖이다.

## 하지 않을 것

- 리팩터링 대상을 발견해도 승인 없이 바로 고치지 않는다.
- 테스트가 깨졌다고 assertion을 완화하거나 테스트를 고쳐서 통과시키지 않는다 — 구현을 되돌리거나 다른 접근을 쓴다.
- 여러 항목을 한꺼번에 고치고 나중에 몰아서 테스트하지 않는다 — 하나 고치고 바로 확인한다.
- 리팩터링 결과를 커밋하거나 푸시하지 않는다.
- 이 프로젝트가 의도적으로 내린 구조 결정(예: `docs/features/tag/prd.md`의 ADR — 유틸/훅으로 추출하지 않기로 한 것)을 "개선"이라는 이름으로 뒤집지 않는다 — 그런 항목이 눈에 띄면 리팩터링 목록이 아니라 별도 논의 사항으로 보고한다.
