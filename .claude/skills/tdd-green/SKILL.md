# tdd-green

TDD의 Green 단계만 담당하는 스킬이다. `tdd-red`가 만들어 둔 실패 중인 테스트를 입력으로 받아, **테스트 하나를 통과시킬 최소한의 구현을 쓰고 → 즉시 실행해 통과와 무회귀를 확인한 뒤 → 이슈 문서를 체크하고 → 다음 실패 테스트로 넘어간다.** 리팩터링이나 커버리지를 올리기 위한 추가 작업은 이 단계의 일이 아니다.

입력: GitHub 이슈 번호 (`$ARGUMENTS`, 예: `/tdd-green 1`)

## 왜 "하나 통과시키고 바로 재확인"인가

여러 테스트를 한꺼번에 구현하고 나중에 몰아 실행하면, 어떤 코드 변경이 어떤 테스트를 통과시켰는지, 혹은 다른 테스트를 깨뜨렸는지 구분하기 어렵다. 하나씩 통과시키고 즉시 전체를 재실행하면 회귀가 생기는 순간 바로 원인을 좁힐 수 있다. 이는 `tdd-red`의 "쓰고 나서 바로 실행" 원칙과 대칭을 이룬다.

## 실행 순서

### 1. 실패 테스트 확인

`npm test`를 실행해 실패 목록을 확인한다.

이슈 문서 위치는 `docs/features/*/issue-{번호}.md`를 글롭 검색해 확정한다(`{번호}`는 `$ARGUMENTS`). 정확히 하나만 매칭되어야 `feature`가 결정된다 — 매칭이 없으면 `test-scenarios`와 `tdd-red`가 아직 실행되지 않은 것이므로, 먼저 그 두 스킬로 시그니처 승인과 Red 테스트 작성을 끝내라고 안내하고 중단한다. 이 문서는 두 절로 구성되어 있다: "1단계 — 확정된 시그니처"(어떤 파일에 어떤 함수/컴포넌트 상태/핸들러가 있어야 하는지)와 "2단계 — 테스트 시나리오"(컴포넌트/RTL 시나리오는 `**시나리오 N — ...**` 굵은 제목으로, 수동 시나리오는 별도 절로 나열됨 — 수동 시나리오는 코드로 옮겨지지 않으므로 이 스킬의 대상이 아니다).

### 2. Collect 실패 감지

이슈 문서의 "컴포넌트(RTL) 시나리오" 절에서 `**시나리오 N —` 개수(수동 시나리오 제외)를 세고, 방금 `npm test` 결과의 `Tests` 총수와 비교한다.

- **일치하면** 정상이다 — 테스트 파일이 전부 collect되어 각 시나리오가 실제로 실행되고 있다는 뜻이니 3번으로 진행한다.
- **불일치하면** import 대상 모듈 자체가 존재하지 않아 vitest가 해당 테스트를 아예 collect하지 못한 것이다(예: `Cannot find module`). 이 경우 이슈 문서 "1단계 — 확정된 시그니처" 절에 나온 파일 경로와 시그니처 그대로, **바디 없이** stub 파일을 만든다 — export되는 함수/컴포넌트가 시그니처대로 존재하기만 하면 된다(타입을 만족하는 최소 반환값이나 `throw new Error('not implemented')` 정도만 허용, 실제 로직은 금지). `npm test`를 다시 실행해 개수가 맞는지 확인한다. **그래도 불일치하면**(stub으로도 해결되지 않는 경우) 원인을 개발자에게 보고하고 중단한다 — 시그니처를 임의로 다시 해석하거나 구현을 앞서 채우지 않는다.

### 3. 디자인 컨텍스트 로드

지금 통과시키려는 실패 테스트의 대상이 **시각적 출력이 있는 UI 컴포넌트**일 때만 이 단계를 수행한다. 순수 함수나 `api/notes.ts` 같은 비-UI 코드라면 건너뛴다.

- `docs/design-system.md` 파일이 있으면 읽어서 구현 대상 컴포넌트의 시각 스펙(색상, 간격, 레이아웃, 상태별 표현)을 파악한다.
- 없으면(이 프로젝트가 그렇다) `design-system` Skill을 호출해 `docs/design-system/`에서 관련 파일을 연다 — 임의로 색상 hex나 Tailwind 값을 짓지 않는다.
- 이슈 문서(`docs/features/{feature}/issue-{번호}.md`)에 "디자인 참고" 절이 있으면 함께 확인한다.
- 위 두 경로 모두에서 디자인 정보를 전혀 찾을 수 없으면(신규 컴포넌트인데 디자인 스펙 자체가 없는 경우) 개발자에게 보고하고 중단한다 — 스타일을 감으로 지어내지 않기 위한 안전장치다.

### 4. 첫 번째 실패 테스트를 통과시키는 최소 구현

실패 목록 중 **하나만** 골라 통과시킬 코드를 쓴다.

- 테스트가 요구하는 동작만 구현한다 — 아직 실패하지 않은 다른 테스트를 미리 대비한 코드를 함께 쓰지 않는다.
- UI 컴포넌트라면 3단계에서 확인한 Tailwind 클래스, 레이아웃 구조, 상태별 표현을 그대로 적용한다. 디자인 문서에 없는 시각 요소(색상, 그림자, 간격 등)를 임의로 추가하지 않는다.
- 이 프로젝트의 기존 패턴(`CLAUDE.md`)을 따른다 — API 함수는 `API_URL` 상수/`res.ok` 체크/한국어 `Error`, 컴포넌트는 named export와 `<Component>Props` 네이밍, CRUD는 `create`/`update`/`delete` 접두사, 에러 처리는 `alert()` 대신 `console.error()`.

### 5. 피드백 루프

```bash
npx vitest run <테스트 파일 경로>
```

으로 방금 작업한 테스트가 통과하는지 확인한 뒤, `npm test`로 전체 테스트에 회귀가 없는지 확인한다.

- **아직 실패 중이면**: 에러 메시지를 읽고 원인을 분석해 코드를 수정한 뒤 5번을 다시 수행한다. 같은 테스트에 대해 **최대 5회** 반복한다.
- **5회를 넘겨도 실패하면**: 개발자에게 실패 원인(마지막 에러 메시지, 시도한 접근들)을 보고하고 중단한다 — 테스트를 통과시키려고 assertion의 의도를 벗어난 우회 코드를 쓰지 않는다.
- **다른 테스트가 깨졌다면**: 방금 작성한 구현이 다른 컴포넌트/함수에 영향을 준 것이므로 원인을 찾아 고친 뒤 전체를 다시 확인한다.

### 6. 이슈 문서 체크

방금 통과시킨 시나리오의 `**시나리오 N — ...**` 줄 앞에 `- [x] `를 붙여 완료를 표시한다.

```diff
- **시나리오 1 — 태그 입력 후 Enter로 칩이 렌더링된다** (AC-1.1)
+ - [x] **시나리오 1 — 태그 입력 후 Enter로 칩이 렌더링된다** (AC-1.1)
```

### 7. 다음 실패 테스트로 이동

남은 실패 테스트가 있으면 4번부터 반복한다. 모두 통과할 때까지 계속한다.

### 8. 전체 통과 후 커버리지 측정

```bash
npx vitest run --coverage
```

미커버 라인이 있으면 확인한다. 그 라인이 이슈 문서의 시나리오에서 애초에 다루지 않은 케이스라면(범위 밖) 개발자에게 보고만 한다 — **커버리지를 올리기 위해 새 테스트를 추가하지 않는다.** 이 스킬은 `tdd-red`가 정한 테스트 범위 안에서만 구현한다. 커버리지 결과는 참고용이다.

### 9. 결과 요약

작업이 끝나면 결과를 요약해 보여준다 — 몇 개의 테스트를 Green으로 만들었는지, stub 파일을 생성했다면 어떤 파일인지, 이슈 문서에 몇 개를 체크했는지, 커버리지에서 발견된 미커버 라인이 있다면 무엇인지, 남은 작업(다른 TAG-N 이슈 등)이 있다면 무엇인지.

## 제약 — 반드시 지킬 것

- **테스트에 없는 기능은 구현하지 않는다.** 이슈 문서의 시나리오가 스코프의 전부다 — "이 김에 같이 하면 좋을 것 같은" 기능을 끼워 넣지 않는다.
- **테스트 파일(`*.test.ts` / `*.test.tsx`)을 수정하지 않는다.** 테스트를 통과시키기 어렵다고 assertion을 완화하거나 테스트 자체를 고치고 싶은 유혹이 들어도 하지 않는다 — assertion이 잘못됐다고 판단되면 구현이 아니라 `tdd-red`/`test-scenarios` 단계로 돌아가야 할 문제이니 개발자에게 알린다.
- **불필요한 추상화를 만들지 않는다.** 테스트가 요구하는 것보다 더 유연한 헬퍼/유틸/설정을 미리 만들지 않는다 — 이 프로젝트는 ADR로 "별도 유틸/훅으로 추출하지 않음" 같은 결정을 명시적으로 내리는 경우가 있으니(`docs/features/tag/issues.md` TAG-3 참고) 이슈 문서에 그런 지시가 있으면 그대로 따른다.
- **디자인 문서에 없는 시각 요소를 임의로 추가하지 않는다.** 스타일은 적용하되, 문서에 없는 색상/그림자/애니메이션 등을 감으로 채우지 않는다.

## 하지 않을 것

- stub 파일에 실제 로직을 채우지 않는다 — stub은 collect 실패를 해소하기 위한 시그니처 껍데기일 뿐, 구현은 4번 단계에서 테스트별로 진행한다.
- 시나리오에 없는 assertion에 대응하는 코드를 미리 작성하지 않는다.
- `alert()`을 쓰지 않는다 — 이 프로젝트는 에러 처리를 `console.error()`로 통일한다.
- 여러 테스트를 한꺼번에 구현하고 나중에 몰아서 검증하지 않는다 — 하나 통과 확인 후 다음으로 넘어간다.
- 커버리지를 올리기 위한 목적으로 테스트를 추가하지 않는다.
