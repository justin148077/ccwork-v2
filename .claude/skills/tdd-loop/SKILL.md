# tdd-loop

`CLAUDE.md`의 "Workflow: TDD 이슈 사이클" 7단계를, 이슈 번호 하나로 시작해서 순서대로 이어 붙이는 컨테이너 스킬이다. **새로운 판단 로직을 추가하지 않는다** — 각 단계에서 무엇을, 어떻게, 언제 사람에게 확인받을지는 이미 `test-scenarios`/`tdd-red`/`tdd-green`/`tdd-refactor`/`security-review`/`create-pr`/`ac-verifier`가 결정해 놓았다. 이 스킬이 하는 일은 그 7개를 올바른 순서로, 올바른 인자로, 이전 단계가 실제로 끝난 뒤에만 호출하는 것뿐이다.

입력: GitHub 이슈 번호 (`$ARGUMENTS`, 예: `/tdd-loop 1`)

## 왜 컨테이너가 필요한가

이슈 하나를 끝까지 끌고 가려면 7개의 스킬/에이전트를 정확한 순서로, 매번 같은 이슈 번호를 넘겨가며 호출해야 한다. 사람이 매 이슈마다 이 순서를 손으로 챙기면 단계를 건너뛰거나(예: `ac-verifier` 없이 바로 리팩터링), 브랜치를 잘못 잡거나(스펙 브랜치가 아니라 `main`에서 분기), 이전 단계가 끝나지 않았는데 다음 단계를 부르는 실수가 생긴다. 이 스킬은 그 순서와 사전 조건만 기계적으로 보장한다 — 각 단계 안에서 무엇을 승인받을지는 건드리지 않는다. 승인 게이트를 컨테이너 레벨에서 다시 만들면 각 하위 스킬이 이미 정교하게 설계해 둔 게이트(예: `test-scenarios`의 2단계 승인, `tdd-refactor`의 항목별 승인)와 이중으로 겹쳐 오히려 "누구에게 무엇을 승인받았는지"가 흐려진다.

## 실행 모델 — 어떻게 "이어 붙이는가"

이 스킬(및 이 스킬이 호출하는 하위 스킬)은 별도 프로세스가 아니라 지금 이 대화 안에서 그대로 실행된다. 즉 `Skill` 도구로 `test-scenarios`를 호출하면, 그 스킬의 지시사항이 이 대화에 로드되어 **이후 여러 턴에 걸쳐** 그 스킬의 승인 게이트를 그대로 따른다 — 사용자가 승인 메시지를 보낼 때까지 몇 턴이 걸리든 상관없다. 컨테이너의 역할은:

1. 지금 몇 번째 단계인지 계속 추적한다.
2. 한 단계가 **완전히 끝났다는 신호**(아래 "완료 판정" 참고)가 나오면, 별도로 묻지 않고 곧바로 다음 단계의 스킬/에이전트를 호출한다.
3. 완료 신호 대신 **중단 신호**(스킬 자체가 실패를 보고하거나, 재시도 한도를 넘기거나, 사전 조건이 깨진 경우)가 나오면, 어느 단계에서 왜 멈췄는지 명확히 보고하고 컨테이너 진행을 멈춘다.

"완료됐는데도 다음 단계로 넘어가기 전에 다시 한번 물어보는 것"은 이 스킬이 하지 말아야 할 일이다 — 사용자가 이미 그 단계의 산출물을 승인했다면(예: PR 초안 승인), 그 승인이 다음 단계로 넘어갈 신호다.

## 실행 순서

### 0단계 — 사전 점검

이후 7단계 전부가 올바른 브랜치, 올바른 이슈를 대상으로 진행되도록 보장하는 단계다. 아래 순서대로 확인하고, **하나라도 실패하면 그 지점에서 사유를 알리고 전체를 중단한다** — 다음 항목으로 넘어가거나 임의로 추측해서 채우지 않는다.

1. `gh issue view $ARGUMENTS` — 이슈가 존재하는지, 본문과 AC(완료조건)가 있는지 확인한다. 이슈가 없거나 접근 실패하면 중단.
2. `git status` — 커밋되지 않은 변경(staged/unstaged/untracked)이 있으면 중단한다. 지금 작업 중이던 다른 내용을 밟고 지나가지 않기 위한 안전장치다. 변경사항을 커밋하거나 정리한 뒤 다시 불러달라고 안내한다.
3. **이슈가 속한 feature spec 판별**: `docs/features/*/issues.md`를 검색해 이슈 제목/번호와 매칭되는 항목(예: `TAG-1`)을 찾고, 그 파일이 속한 디렉터리명을 `<spec>`으로 삼는다(예: `docs/features/tag/issues.md` → `<spec> = tag`). 매칭되는 문서가 없으면 추측하지 말고 사용자에게 어느 feature에 속하는지 확인한다.
4. **스펙 브랜치 확인**: `git for-each-ref`로 로컬+원격에서 `feature/<spec>` 계열 브랜치를 찾는다. 정확히 하나 찾으면 그것이 이번 작업의 베이스다. 하나도 없으면 — 이 이슈가 해당 feature의 첫 작업이고 스펙 브랜치 자체가 아직 없다는 뜻이므로, 컨테이너가 임의로 만들지 않고 사용자에게 먼저 스펙 브랜치를 준비해달라고 요청한 뒤 중단한다. 여러 개 후보가 있으면 사용자에게 확인한다(`create-pr`이 베이스 브랜치를 못 찾을 때와 같은 원칙 — 애매하면 추측하지 않는다).
5. 현재 브랜치가 3~4번에서 정한 `feature/<spec>`가 아니면 그 브랜치로 checkout한다(로컬에 없고 원격에만 있으면 추적 브랜치로 checkout).
6. **이슈 브랜치 이름 결정**: `feat/<이슈번호>-<kebab-slug>` 형식을 쓴다. `<kebab-slug>`는 이슈 제목을 2~4단어의 영문 kebab-case로 요약한 것 — 이 저장소에 실제로 있는 `fix/8-tag-not-saved`(이슈 #8) 같은 브랜치명과 같은 패턴이다.
7. 그 이슈 브랜치가 이미 로컬 또는 원격에 존재하면 **동일 이슈의 재실행**으로 간주한다. 조용히 덮어쓰거나 조용히 이어 쓰지 않는다 — `AskUserQuestion`으로 "기존 브랜치를 이어서 쓸지 / 삭제 후 새로 시작할지(덮어쓰기, 파괴적) / 중단할지" 확인받는다. 이어서 쓰기를 선택하면 그 브랜치로 checkout, 덮어쓰기를 선택하면 명시적 확인 후 기존 브랜치를 지우고 4~5번에서 정한 베이스에서 새로 분기, 중단을 선택하면 여기서 끝낸다.
8. 존재하지 않으면 베이스 브랜치에서 새로 분기해 checkout한다: `git checkout -b feat/<이슈번호>-<slug>`.

0단계가 모두 끝나면 어떤 브랜치에서 시작하는지 한 줄로 알리고 1단계로 진행한다.

### 1단계 — `/test-scenarios $ARGUMENTS`

`Skill` 도구로 `test-scenarios`를 이슈 번호와 함께 호출한다. 이 스킬 내부에는 두 개의 하드 게이트가 있다 — 시그니처 확정 승인, 그리고 승인된 시그니처를 바탕으로 한 테스트 시나리오 도출. 둘 다 그대로 유지된다: 컨테이너는 개입하지 않고, 사용자가 각 게이트를 실제로 승인할 때까지 기다린다.

**완료 판정**: `docs/features/<spec>/issue-<번호>.md`가 "1단계 — 확정된 시그니처"와 "2단계 — 테스트 시나리오" 두 절을 모두 갖춘 채 생성되어 있으면 완료다. 완료되면 곧바로 2단계로 진행한다.

### 2단계 — `/tdd-red $ARGUMENTS`

`Skill` 도구로 `tdd-red`를 호출한다. 1단계 산출물(`issue-<번호>.md`)의 시나리오를 하나씩 실패하는 테스트로 옮기고, 옮길 때마다 즉시 실행해 실패를 확인하는 것까지가 이 스킬 자체의 동작이다 — 이 과정에는 사용자 승인 게이트가 없으므로(테스트 코드만 다루는 단계) 중간에 멈추지 않는다.

**완료 판정**: 이번 이슈에서 새로 추가한 테스트가 전부 Red 상태이고, `npm test`로 기존 테스트에 회귀가 없다는 결과 요약이 나오면 완료다. 완료되면 곧바로 3단계로 진행한다.

### 3단계 — `/tdd-green $ARGUMENTS`

`Skill` 도구로 `tdd-green`을 호출한다. 실패 테스트를 하나씩 최소 구현으로 통과시키고, 통과할 때마다 전체 테스트로 회귀를 확인한다. 같은 테스트에 대해 **최대 5회**까지 재시도하는 루프가 스킬 내부에 이미 있다 — 컨테이너가 별도로 재시도 횟수를 세지 않는다.

시작 직후 이 스킬은 **collect 실패**를 자체적으로 감지한다 — 이슈 문서의 시나리오 개수와 `npm test`가 실제로 collect한 테스트 개수가 안 맞으면(즉, import 대상 모듈 자체가 없어 vitest가 테스트를 아예 실행하지 못하면), 확정된 시그니처 그대로 **바디 없는 stub 파일**을 만들어 collect를 맞춘 뒤에야 4단계(최소 구현)로 넘어간다. 이것도 `tdd-green` 내부의 정해진 절차라 컨테이너는 개입하지 않고 결과만 전달받는다 — stub 생성 자체는 승인 게이트가 아니다.

**완료 판정**: 모든 실패 테스트가 Green이 되고 `npm test` 전체가 통과하면 완료다.
**중단 판정**: 어느 테스트가 5회 재시도 후에도 통과하지 못해 `tdd-green`이 스스로 중단을 보고하면, 컨테이너도 여기서 멈추고 어떤 테스트가 왜 막혔는지 그대로 전달한다.

### 4단계 — `@ac-verifier $ARGUMENTS`

`Agent` 도구로 `subagent_type: ac-verifier`를 호출한다. 이 에이전트는 매번 새로 시작하는 컨텍스트이므로, 프롬프트에 이슈 번호와 함께 "Green이 끝난 이슈의 Acceptance Criteria 충족 여부를 독립적으로 검증해달라"는 지시를 자체적으로 완결되게 담는다 (`gh issue view` 등은 에이전트가 스스로 수행한다).

`ac-verifier`는 스킬이 아니라 검증 리포트를 내는 에이전트라 자체 승인 게이트가 없다 — 그래서 갭 처리는 컨테이너가 직접 맡는다:

- 모든 AC가 ✅면 곧바로 5단계로 진행한다.
- 하나라도 ⚠️(부분 충족) 또는 ❌(미충족)이면 **여기서 멈춘다.** 에이전트가 제시한 갭과 제안된 보완 시나리오를 그대로 사용자에게 보여주고, 어떻게 할지 묻는다 (예: `tdd-red`로 돌아가 시나리오를 보완할지, 갭을 인지한 채로 진행할지는 사용자가 정한다). 컨테이너가 임의로 갭을 무시하고 5단계로 넘어가지 않는다.

### 5단계 — `/tdd-refactor $ARGUMENTS`

`Skill` 도구로 `tdd-refactor`를 호출한다. 리팩터링 대상을 먼저 목록으로 제시하고 승인받은 뒤에만 하나씩 고치며, 항목마다 `npm test`로 무회귀를 확인하는 것은 이 스킬 자체의 하드 게이트다 — 그대로 유지된다.

**완료 판정**: 승인된 항목을 모두 처리(또는 스킵)하고 전체 테스트가 통과한다는 결과 요약이 나오면 완료다("리팩터링할 게 없습니다"로 끝나는 경우도 완료로 취급한다). 완료되면 곧바로 6단계로 진행한다.

### 6단계 — `/security-review $ARGUMENTS`

`Skill` 도구로 `security-review`를 호출한다. `npx tsc --noEmit`(타입 오류), `npm audit`(의존성 취약점), `.env` 노출·`import.meta.env` 참조 스캔(보안 패턴 점검) 세 가지를 모아 "즉시 수정 필요 / 권장 수정 / 무시 가능"으로 분류하고, "즉시 수정 필요" 항목만 승인 후 고치는 것은 이 스킬 자체의 하드 게이트다 — 그대로 유지된다.

**완료 판정**: 재스캔 결과 "즉시 수정 필요" 항목이 더 이상 없다는 결과 요약이 나오면 완료다("권장 수정"/"무시 가능" 항목이 남아 있는 것은 정상이며 완료를 막지 않는다). 완료되면 곧바로 7단계로 진행한다.

### 7단계 — `/create-pr`

1. **commitlint 사전 확인**: 이번 이슈 작업으로 생긴 커밋들이 이미 `git commit` 시점에 husky `commit-msg` 훅을 통과했겠지만, 안전 차원에서 한 번 더 확인한다.
   ```bash
   npx commitlint --from <0단계에서 정한 베이스 브랜치> --to HEAD
   ```
   실패하는 커밋이 있으면(예: 훅을 우회해 커밋된 경우) 어떤 커밋이 왜 실패하는지 보고하고 중단한다 — 커밋 메시지를 컨테이너가 임의로 rewrite하지 않는다(히스토리 수정은 파괴적 작업이라 사용자 판단이 필요하다).
2. `Skill` 도구로 `create-pr`를 호출하되, 베이스 브랜치를 0단계에서 이미 확정한 `feature/<spec>`로 명시해서 넘긴다(`create-pr`는 `$ARGUMENTS`로 베이스 브랜치를 받을 수 있다) — 자체 추론에 맡기지 않는다.
3. `create-pr`가 PR 초안(제목/본문)을 제시하면, 본문에 `Closes #$ARGUMENTS`가 포함되어 있는지 확인한다. 빠져 있으면 승인 전에 사용자에게 알려 추가하도록 요청한다 — 초안 자체를 컨테이너가 대신 고치지 않는다. 이 초안 승인/거부, 그리고 E2E 실패 시의 중단·안내는 전부 `create-pr` 자체의 하드 게이트이므로 그대로 유지된다.
   - `create-pr`가 "커밋 안 된 변경이 있다"며 자체적으로 멈추는 경우도 있다 — 5~6단계 산출물을 아직 커밋하지 않았다면 정상적으로 여기서 멈춘다. 컨테이너가 대신 커밋하지 않는다(커밋은 사용자가 명시적으로 요청했을 때만 한다). 사용자가 커밋을 마치고 "계속 진행해줘"라고 하면, 컨테이너는 7단계 2번(`create-pr` 호출)부터 다시 시작한다.
4. `create-pr`가 PR을 실제로 생성해 URL을 반환하면, 그 PR을 이슈에 링크로 남긴다:
   ```bash
   gh issue comment $ARGUMENTS --body "PR: <PR URL>"
   ```
   이 코멘트는 별도 승인을 다시 묻지 않는다 — PR 생성 승인(3번)에 이미 포함된 마무리 동작으로 취급한다.

**완료 판정**: PR이 생성되고 이슈에 링크 코멘트가 달리면 7단계, 그리고 이 컨테이너 전체가 완료다. squash merge와 이슈 클로즈는 `CLAUDE.md`가 명시한 대로 이 스킬의 범위 밖 — 사용자가 GitHub에서 직접 처리한다.

## 특징 — 컨테이너가 지키는 원칙

- 각 단계 호출 사이에는 "지금 N단계를 시작합니다" 같은 짧은 진행 메시지만 출력한다. 하위 스킬의 산출물(시그니처, 리팩터링 목록, 보안 등급, PR 초안 등)을 컨테이너가 요약하거나 대신 판단하지 않는다 — 그 스킬이 원래 출력하는 그대로 사용자에게 전달되게 둔다.
- 각 하위 스킬 내부의 승인 게이트는 그대로 작동한다. 승인이 필요한 지점에서는 실제로 사용자의 응답이 올 때까지, 몇 턴이 걸리든 컨테이너가 다음 단계를 부르지 않는다.
- 컨테이너 자신은 "다음 단계로 진행할까요?" 같은 추가 확인 질문을 만들지 않는다. 어떤 단계가 완료 판정을 받으면 곧바로 다음 단계를 호출한다 — 예외는 이 문서에 명시된 것뿐이다(0단계의 브랜치 충돌 확인, 4단계의 AC 갭 보고).
- 어느 단계에서든 중단 판정이 나오면, "N단계(스킬 이름)에서 중단됨 — 이유"를 명확히 출력하고 멈춘다. 다음 단계를 시도하지 않는다.

## 하지 않을 것

- 하위 스킬이 요구하는 승인을 컨테이너가 대신 하거나 추측하지 않는다.
- 하위 스킬의 산출물(시그니처, 시나리오, 리팩터링 항목, 보안 등급, PR 초안)을 컨테이너가 임의로 수정하지 않는다 — 문제를 발견하면 사용자에게 알리고 해당 스킬의 승인 단계에서 반영되게 한다.
- 커밋을 대신 하지 않는다 — 사용자가 명시적으로 요청하지 않는 한, 7단계에서 커밋되지 않은 변경을 만나면 멈추고 안내만 한다.
- 브랜치가 이미 존재하는데 확인 없이 덮어쓰거나 삭제하지 않는다.
- squash merge, 이슈 클로즈를 대신 수행하지 않는다 — `create-pr`가 PR을 여는 데까지만 이 컨테이너의 범위다.
- 실패/중단 지점을 숨기거나 "일단 다음 단계로 넘어가서" 진행하지 않는다.
