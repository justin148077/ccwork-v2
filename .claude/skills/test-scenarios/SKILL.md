# test-scenarios

이슈 하나를 구현하기 전에 "이 이슈가 코드에 어떤 표면(시그니처)을 남기는가"를 먼저 확정하고, 개발자 승인을 받은 뒤에만 그 표면에 대한 테스트 시나리오를 도출하는 스킬이다. 목적은 구현(코드 작성)과 TDD 테스트 코드 작성 그 이전 단계 — "무엇을 테스트할 것인가"를 코드 없이 먼저 합의하는 것이다.

이 스킬은 **구현 코드를 작성하지 않는다.** 시그니처/타입/인터페이스와, 승인 후의 테스트 시나리오 텍스트만 산출한다.

입력: GitHub 이슈 번호 (`$ARGUMENTS`, 예: `/test-scenarios 1`)

## 왜 두 단계로 나뉘는가

시그니처를 먼저 확정하지 않고 테스트 시나리오부터 쓰면, 나중에 시그니처가 바뀔 때 시나리오도 다시 써야 한다. 반대로 시그니처를 개발자 승인 없이 확정하면, 이 프로젝트의 기존 패턴(예: `updateNote(id, { title, content, tags })`처럼 부분 업데이트를 객체로 받는 방식, `create`/`update`/`delete` 접두사 통일)과 어긋난 채로 시나리오까지 만들어져 재작업이 커진다. 그래서 1단계 산출물을 반드시 사람이 보고 확인한 뒤에만 2단계로 넘어간다.

## 1단계 — 시그니처 확정 (매 실행마다 항상 수행)

### 1-1. 근거 수집

- `gh issue view <번호>`로 이슈 본문을 읽는다.
- 이슈 번호가 `docs/features/tag/issues.md`의 TAG-N과 어떻게 대응하는지 확인한다 (제목으로 매칭). 이 문서에 있는 "영향 범위", "완료조건(AC)" 절이 시그니처 설계의 1차 재료다.
- `docs/features/tag/prd.md` (배경·ADR)와 `docs/features/tag/spec-fixed.md`(있다면, 동작의 정본)를 읽는다. `issues.md`와 두 문서가 어긋나면 `prd.md`/`spec-fixed.md`가 우선이라고 `issues.md` 자체에 적혀 있으므로 그 우선순위를 따른다.
- 현재 코드베이스에서 관련 파일을 읽는다 — 최소한 `src/types/note.ts`, `src/api/notes.ts`, `src/context/NotesContext.tsx`, 그리고 이슈가 건드리는 컴포넌트(`src/components/NoteEditor.tsx` 등). 새로 추가하는 시그니처가 아니라 **기존 시그니처와 어떻게 이어지는지**를 파악하는 것이 목적이다.

### 1-2. 시그니처 산출

아래 세 가지를 필요한 범위 내에서 작성한다 (이슈가 건드리지 않는 영역은 생략):

- **함수 시그니처** — 이름, 파라미터 타입, 반환 타입. `api/notes.ts`에 함수를 추가/변경한다면 그 함수의 시그니처, `NotesContext`의 액션 함수라면 그 시그니처, 컴포넌트 내부 핸들러(`handleAddTag` 등)라면 그 시그니처.
- **에러 케이스** — 어떤 조건에서 에러를 던지는지, 그리고 이 프로젝트의 기존 패턴대로 한국어 에러 메시지를 던진다면 그 메시지 문구까지 (`res.ok` 체크 실패 시 `throw new Error('...')` 패턴, 루트 `CLAUDE.md`의 "API 호출 패턴" 참고). 클라이언트 측 검증 실패(예: 빈 문자열, 중복)는 이 프로젝트에서 `alert` 없이 `console.error`로만 처리하므로, "에러를 던진다"가 아니라 "무엇을 조건으로 거부하고 어떤 로그를 남기는지"로 표현한다.
- **컴포넌트 Props 타입** — 새로 추가되거나 바뀌는 props가 있다면 `interface <Component>Props { ... }` 형태로.

**반드시 지킬 것 — 구현 코드 금지**: 함수 바디를 작성하지 않는다. 타입 시그니처와 (필요하다면) 에러를 던지는 조건을 한 줄로 설명하는 것까지만 허용된다. `{ ... }` 나 `// TODO` 같은 자리표시자로 바디를 대신한다. 실제로 `if`/`for`/상태 갱신 로직을 쓰고 있다면 범위를 벗어난 것이다.

**반드시 지킬 것 — 기존 패턴을 따를 것**: 새 패턴을 발명하지 않는다. 루트 `CLAUDE.md`의 다음 절을 참고 기준으로 삼는다.

- "API 호출 패턴" — `API_URL` 상수, `res.ok` 체크, 한국어 `Error` 메시지, `createNote`/`updateNote`가 내부에서 `createdAt`/`updatedAt`을 채우는 방식
- "컴포넌트 구현 패턴" — named export, `<Component>Props` 네이밍, Tailwind 유틸리티 우선
- "네이밍 패턴" — CRUD는 `create`/`update`/`delete` 접두사(동의어 금지), boolean은 `is` 접두사, 이벤트 핸들러는 `handle`, 콜백 props는 `on` 접두사

이슈 문서(`issues.md`)에 이미 시그니처 힌트가 명시된 경우(예: TAG-1의 `updateNote(id, { title, content, tags })`) 그것과 모순되는 시그니처를 만들지 않는다 — 그 힌트를 정식 타입으로 구체화하는 것이 이 단계의 일이다.

### 1-3. 제시 및 승인 대기 — 하드 게이트

확정한 시그니처를 채팅 응답에 코드 블록으로 정리해 보여주고, 개발자에게 확인을 요청한다. 예: "이 시그니처로 진행해도 될까요? 수정할 부분이 있으면 알려주세요."

**여기서 멈춘다.** 같은 응답 안에서 2단계(테스트 시나리오 도출)로 넘어가지 않는다. 사용자가 침묵하거나 다른 화제로 넘어가는 것을 승인으로 간주하지 않는다 — 이후 메시지에서 "좋아", "진행해", "이걸로 확정" 등 명시적인 승인이 와야 2단계를 시작한다. 사용자가 시그니처에 수정을 요청하면 1단계를 다시 수행해 수정안을 제시하고, 다시 승인을 기다린다.

## 2단계 — 테스트 시나리오 도출 (1단계가 승인된 이후에만)

승인된 시그니처와 이슈의 완료조건(Given/When/Then 형태의 AC, `issues.md` 참고)을 바탕으로 구체적인 테스트 시나리오를 도출한다. 이 단계의 산출물은 **시나리오 텍스트**이지 테스트 코드가 아니다 — 실제 `*.test.tsx` 구현은 이 스킬의 범위 밖이며 이후 별도 TDD 단계에서 진행한다.

시나리오는 다음을 포함해 정리한다:

- 각 AC를 커버하는 시나리오 (AC 1:1 대응이 기본이되, 하나의 AC가 여러 시나리오로 쪼개질 수도 있다)
- 시나리오 종류 구분 — `issues.md`의 "테스트 계획" 절이 쓰는 구분(컴포넌트/RTL, 수동)을 따른다
- 각 시나리오: 무엇을 준비하고(Given) 무엇을 하고(When) 무엇을 확인하는지(Then), 그리고 1단계에서 확정한 시그니처의 어떤 부분(함수 호출 인자, 에러 로그, 렌더링 결과 등)을 검증 지점으로 삼는지
- 이슈의 "영향 범위"에 없는 동작(예: TAG-1 단계에서는 삭제 UI나 검증 로직이 범위 밖)을 시나리오에 끼워 넣지 않는다 — PRD 4장(Out of Scope)과 해당 이슈의 범위를 벗어난 시나리오는 만들지 않는다

### 2단계 산출물 저장

시나리오를 채팅에 제시한 뒤, 승인된 1단계 시그니처와 함께 `docs/features/<feature>/issue-<번호>.md`로 저장한다 (예: 이슈 #1이면 `docs/features/tag/issue-1.md`). `<feature>`는 `docs/features/` 아래 이 이슈가 속한 기능 디렉터리(이슈 조사 과정에서 이미 확인됨 — 예: `tag`)를 그대로 쓴다. 이 파일은 이 스킬 실행의 기록이자 다음 TDD 단계의 입력 문서이므로, 채팅 응답에만 남기고 끝내지 않는다. 구조는 "1단계 — 확정된 시그니처"와 "2단계 — 테스트 시나리오" 두 절로 나눠, 이 문서 자체가 근거로 삼은 GitHub 이슈 번호·`issues.md`/`prd.md`/`spec-fixed.md` 출처를 상단에 명시한다.

## 하지 않을 것

- 구현 코드(함수 바디, JSX, 상태 갱신 로직)를 쓰지 않는다.
- 1단계 승인 없이 2단계로 넘어가지 않는다 — 한 턴 안에서 자동으로 이어가지 않는다.
- 이슈가 다루지 않는 범위(다른 TAG-N 이슈, PRD Out of Scope 항목)까지 시그니처나 시나리오를 확장하지 않는다.
- `alert()`을 쓰는 에러 처리 시그니처를 만들지 않는다 — 이 프로젝트는 `console.error`로 통일되어 있다.
