# tdd-red

TDD의 Red 단계만 담당하는 스킬이다. `test-scenarios` 스킬이 만든 `docs/features/tag/issue-{번호}.md`(승인된 시그니처 + Given/When/Then 시나리오)를 입력으로 받아, 시나리오 하나하나를 실제 테스트 코드로 옮기고, **작성한 즉시 실행해서 "구현이 없어서 실패하는" 것까지 직접 확인한다.**

입력: GitHub 이슈 번호 (`$ARGUMENTS`, 예: `/tdd-red 1`)

## 왜 "쓰고 나서 바로 실행"인가

Red 단계의 목적은 테스트 코드 자체가 맞는지를 구현 없이 미리 검증하는 것이다. 시나리오를 전부 쓴 뒤 한꺼번에 실행하면, 테스트 자체의 문법 오류·잘못된 셀렉터·mock 설정 실수와 "구현이 없어서 나는 실패"가 뒤섞여 구분하기 어렵다. 하나씩 쓰고 바로 돌리면 실패 원인이 항상 "아직 구현이 없다" 하나로 좁혀지고, 이 실패가 다음 단계(Green)에서 무엇을 구현해야 신호가 사라지는지 보여주는 기준선이 된다.

## 실행 순서

### 1. 근거 읽기

`docs/features/tag/issue-{번호}.md`를 읽는다. 이 파일에는 두 절이 있다:

- **1단계 — 확정된 시그니처**: 어떤 파일에 어떤 함수/컴포넌트 상태/핸들러가 생기는지. 테스트가 무엇을 import/렌더링/호출할지는 여기서 나온다.
- **2단계 — 테스트 시나리오**: Given/When/Then 형태의 시나리오 목록과 각 시나리오의 "검증 지점".

파일이 없다면 `test-scenarios` 스킬이 아직 실행되지 않았거나 승인되지 않은 것이다 — 시그니처를 임의로 지어내 테스트를 쓰지 말고, 먼저 `test-scenarios`로 이 이슈의 시그니처/시나리오를 확정하라고 안내한다.

이어서 시그니처가 가리키는 실제 소스 파일(예: `src/components/NoteEditor.tsx`, `src/types/note.ts`)을 읽어 현재 상태를 확인한다 — 아직 구현되지 않았으므로 시그니처에 언급된 필드/핸들러는 없는 게 정상이다. 이 시점에 컴포넌트가 context 훅(`useNotes` 등)을 어떻게 쓰는지도 함께 확인해 mock 방식을 결정한다.

### 2. 시나리오를 하나씩 테스트로 옮긴다

시나리오 목록을 순서대로 처리한다. **한 시나리오를 코드로 옮기고 → 즉시 실행해 실패를 확인한 뒤 → 다음 시나리오로 넘어간다.** 여러 시나리오를 한번에 몰아 쓰고 나중에 몰아서 실행하지 않는다.

- **테스트 이름**: `should [기대 동작] when [조건]` 형식의 `it(...)` 설명으로 옮긴다. 시나리오의 Then이 "기대 동작", Given/When이 "조건"이 된다.
  예) 시나리오 "태그 입력 후 Enter로 태그가 확정되어 칩으로 보인다" → `it('should render a chip when a tag is entered and Enter is pressed', ...)`
- **도구**: Vitest(`describe`/`it`/`expect`/`vi`) + `@testing-library/react`(`render`/`screen`) + `@testing-library/user-event`. `vite.config.ts`에 `globals: true`가 설정되어 있어 `describe`/`it`/`expect`를 import 없이 쓸 수 있지만, 이 프로젝트에 기존 테스트 파일이 없어 확립된 관례가 없으므로 명시적 import를 써도 무방하다 — 파일 안에서 일관되게만 쓴다.
- **시나리오의 "검증 지점"을 그대로 assertion으로 옮긴다.** 예를 들어 시나리오가 "`updateNote`가 `tags`를 포함해 호출된다"고 하면 `expect(updateNoteMock).toHaveBeenCalledWith(...)`로, "칩이 보인다"면 `expect(screen.getByText('react')).toBeInTheDocument()`로 옮긴다. 시나리오에 없는 assertion을 새로 추가하지 않는다 — 검증 범위를 넓히는 건 이 단계의 일이 아니다.
- **컴포넌트가 `NotesContext`의 `useNotes()`를 통해 `updateNote` 등을 가져오는 구조**이므로, 시나리오가 `updateNote` 호출 인자를 검증해야 한다면 `vi.mock('../context/NotesContext', ...)` 또는 동등한 방식으로 `useNotes`를 mock해 `updateNote`를 spy 함수로 대체한다. 실제 `NotesProvider`/json-server에 의존하지 않는다 — 수동 시나리오(예: "저장 → 새로고침 후 확인")는 컴포넌트 테스트로 옮기지 않고 그대로 수동 절차로 남겨둔다.
- **수동(Manual) 시나리오는 테스트 코드로 옮기지 않는다.** `issue-{번호}.md`의 "수동 시나리오" 절은 이 스킬의 산출물이 아니다 — 컴포넌트/RTL 시나리오만 코드로 옮긴다.

각 시나리오를 옮긴 직후 해당 파일만 실행한다 (`CLAUDE.md`에 명시된 단일 테스트 실행 방법):

```bash
npx vitest run <테스트 파일 경로>
```

**기대하는 실패와 아닌 실패를 구분한다.**

- 기대하는 실패: 아직 구현이 없어서 요소를 못 찾거나(`Unable to find element`), mock 함수가 기대한 인자로 호출되지 않은 경우 — 이게 정상적인 Red다.
- 기대하지 않은 실패: import 경로 오류, 테스트 파일 자체의 문법 오류, mock 설정 실수로 테스트가 애초에 실행조차 안 되는 경우 — 이건 테스트 코드 버그이므로 그 자리에서 고친다.
- 만약 시나리오를 옮긴 테스트가 **통과해버리면** 즉시 멈추고 원인을 확인한다 — 구현이 없는데 통과한다는 건 assertion이 시나리오의 의도를 검증하지 못하고 있다는 신호다 (예: 항상 참인 조건을 검증하고 있음). 이 경우를 그냥 넘기지 않는다.

### 3. 테스트 파일 컨벤션

- **위치**: 테스트 대상 파일과 같은 디렉토리에 둔다.
  예) `src/components/NoteEditor.tsx`의 동작을 테스트한다면 → `src/components/NoteEditor.test.tsx`
  예) `src/api/notes.ts`의 함수를 테스트한다면 → `src/api/notes.test.ts`
  대상 파일은 시나리오의 "검증 지점"이 어느 시그니처를 가리키는지로 판단한다 (1단계에서 읽은 "확정된 시그니처" 절 기준) — 시나리오 예시에 나온 파일명을 그대로 베끼지 않는다.
- **네이밍**: `{파일명}.test.ts` (순수 함수/API) 또는 `{파일명}.test.tsx` (컴포넌트, JSX 사용).
- **`describe` 블록**: 테스트 대상 함수/컴포넌트 단위로 묶는다. 여러 핸들러/시나리오 그룹이 한 컴포넌트에 있으면 중첩하거나 나눠 쓴다.
  예)
  ```ts
  describe('NoteEditor', () => {
    describe('태그 추가', () => {
      it('should render a chip when a tag is entered and Enter is pressed', () => {
        /* ... */
      });
    });
  });
  ```

### 4. 전체 마무리

모든 시나리오를 옮기고 개별 확인까지 끝났다면 전체 테스트를 한 번 더 돌려 회귀를 확인한다:

```bash
npm test
```

이번 이슈에서 새로 추가한 테스트가 전부 실패 상태인지 확인한다. 이미 존재하는 다른 테스트 파일이 있다면 그것까지 건드리지 않았는지(=계속 통과 상태인지)도 함께 확인한다 — 이 스킬은 테스트 파일만 추가하므로 기존 테스트를 깨뜨렸다면 방금 만든 테스트 파일의 mock/설정이 다른 곳에 영향을 준 것이니 원인을 찾아 고친다.

작업이 끝나면 결과를 요약해 보여준다 — 몇 개의 테스트 파일에 몇 개의 시나리오를 옮겼는지, 전부 Red 상태인지, 다음은 Green(구현) 단계라는 것을 알려준다. Green 단계 자체는 이 스킬의 범위 밖이다.

## 제약 — 반드시 지킬 것

- **테스트 파일만 생성/수정한다.** `*.test.ts` / `*.test.tsx` 이외의 파일은 만들거나 고치지 않는다.
- **`src/` 아래 구현 코드는 절대 수정하지 않는다.** 테스트를 통과시키기 위해 구현을 살짝 손대고 싶은 유혹이 들어도(예: 타입 에러를 피하려고 `Note`에 `tags`를 추가) 하지 않는다 — 그건 Green 단계의 일이며, 지금 구현을 건드리면 Red가 무엇을 확인하는 단계였는지 의미가 사라진다. 테스트가 타입 에러로 막힌다면 그 자체를 실패로 기록하고 넘어간다.
- **시나리오에 없는 테스트를 새로 만들지 않는다.** 이슈 문서의 시나리오 목록이 스코프의 전부다 — 더 꼼꼼해 보이는 추가 케이스가 떠올라도 이 단계에서 끼워 넣지 않는다. (필요하다고 판단되면 `test-scenarios`로 돌아가 시나리오 자체를 보완하도록 사용자에게 제안한다.)
- **한 시나리오를 다 쓰기 전에 다음 시나리오로 넘어가지 않는다.** 실행-확인 없이 여러 시나리오를 몰아 쓰지 않는다.

## 하지 않을 것

- 구현 코드를 작성하거나 고치지 않는다 (`src/` 비-테스트 파일 전부).
- 수동 시나리오를 테스트 코드로 옮기지 않는다.
- 통과하는 테스트를 Red 단계 산출물로 제출하지 않는다 — 통과했다면 assertion이 잘못된 것이니 고친 뒤에야 다음으로 넘어간다.
- `issue-{번호}.md`에 없는 시그니처를 임의로 상상해 테스트를 쓰지 않는다.
